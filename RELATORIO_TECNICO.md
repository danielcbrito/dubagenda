# RELATÓRIO TÉCNICO COMPLETO — DUB AGENDA

---

## ETAPA 1 — VISÃO GERAL DA ARQUITETURA

O DUB Agenda é uma aplicação web mobile-first construída com React 18, TypeScript, Vite como bundler, Tailwind CSS para estilização, shadcn/ui como biblioteca de componentes base, Framer Motion para animações e Supabase como plataforma de backend completa (autenticação, banco de dados PostgreSQL, Edge Functions em Deno e Realtime via WebSockets). O aplicativo funciona como um sistema de agendamento para barbearias com suporte a multi-tenancy, ou seja, múltiplas barbearias podem operar dentro da mesma infraestrutura, cada uma com seus próprios profissionais, serviços, planos e promoções, sendo que o isolamento de dados é garantido por meio de um campo `tenant_id` presente em praticamente todas as tabelas do sistema. O ponto de entrada da aplicação é o arquivo `src/main.tsx`, que monta o componente raiz `<App />` dentro do DOM, e este por sua vez inicializa toda a árvore de providers: o `ThemeProvider` do next-themes para gerenciamento de tema claro/escuro, o `QueryClientProvider` do TanStack React Query para cache de queries (embora a aplicação use predominantemente chamadas diretas ao Supabase SDK ao invés de React Query hooks), o `TooltipProvider` do Radix UI, os componentes de toast (Toaster do shadcn e Sonner), e o `GlobalErrorBoundary` que captura erros não tratados na árvore React e exibe uma tela de fallback amigável ao usuário.

## ETAPA 2 — INICIALIZAÇÃO E SPLASH SCREEN

Quando o aplicativo é aberto, o componente `AppWithSplash` renderiza imediatamente o componente `<SplashScreen />` com a prop `visible={true}`, que exibe uma animação de marca (logo da DUB) por exatamente 2 segundos, controlada por um `setTimeout` dentro de um `useEffect`. Após esse período, o estado `showSplash` é alterado para `false`, fazendo a splash screen desaparecer via animação de saída. Simultaneamente, o `BrowserRouter` do React Router DOM já está montado e o componente `AppRoutes` começa a resolver a rota atual. Dentro de `AppRoutes`, dois guards são ativados antes de qualquer conteúdo ser renderizado: o `AuthSessionGuard` e o `ScrollLockGuard`. O `AuthSessionGuard` registra um listener via `supabase.auth.onAuthStateChange` para monitorar eventos de autenticação como `TOKEN_REFRESHED` e `SIGNED_OUT`, e também faz uma verificação inicial de sessão chamando `supabase.auth.getSession()` — caso a sessão retorne um erro (sessão corrompida, token expirado sem possibilidade de refresh), ele automaticamente chama `supabase.auth.signOut()` e redireciona o usuário para `/auth?mode=login`, evitando loops de erro. O `ScrollLockGuard` é um componente utilitário que, a cada mudança de rota (monitorada via `useLocation()`), limpa todas as propriedades de overflow, position, width, height e touch-action do `<html>` e `<body>`, garantindo que modais e sheets que manipulam scroll não deixem estilos residuais ao serem fechados.

## ETAPA 3 — SISTEMA DE MANUTENÇÃO

Todas as rotas passam pelo componente `MaintenanceWrapper`, que utiliza o hook customizado `useMaintenanceMode`. Este hook consulta a função de banco de dados `get_maintenance_status()` via RPC do Supabase para verificar se o modo de manutenção está ativo, qual a mensagem configurada, se há um aviso prévio ativo e se o usuário atual está na lista de e-mails permitidos (tabela `manutencao_emails_permitidos`). O sistema distingue entre rotas públicas (landing page, autenticação, páginas de barbearia pública via slug) e rotas autenticadas. Se a manutenção estiver ativa e o usuário autenticado não estiver na lista de permitidos, uma tela de manutenção (`MaintenanceScreen`) é exibida no lugar de todo o conteúdo, bloqueando o acesso. Se o usuário estiver na lista de permitidos, ele acessa normalmente mas vê um banner de aviso (`MaintenanceWarningBanner`) no topo da tela. Rotas públicas nunca são bloqueadas pela manutenção.

## ETAPA 4 — ROTEAMENTO E LAZY LOADING

Todas as páginas da aplicação são importadas via `React.lazy()`, o que significa que cada rota gera um chunk separado no bundle do Vite, carregado sob demanda apenas quando o usuário navega para aquela rota. Um componente `<Suspense fallback={<PageLoader />}>` envolve todas as rotas, exibindo um spinner de loading centralizado enquanto o chunk da página é baixado. As rotas são organizadas em dois grupos principais: rotas públicas (definidas no array `PUBLIC_ROUTES`) que incluem `/` (landing page), `/auth` (login/cadastro), `/auth/callback` (callback OAuth), `/verificar-email`, `/verificar-whatsapp`, `/escolher-verificacao`, `/esqueci-senha`, `/resetar-senha`, `/escolher-barbearia`, e rotas dinâmicas de barbearia via slug (`/b/:slug` e `/:slug`); e rotas autenticadas que incluem `/cliente` (dashboard do cliente), `/cliente/agendar` (fluxo de agendamento), `/cliente/assinar` (assinatura de plano), `/cliente/pagamento`, `/cliente/pix-checkout`, `/cliente/assinatura-pix`, `/cliente/carteira` (carteira digital), `/cliente/perfil`, `/cliente/dados-pessoais`, `/cliente/seguranca`, `/cliente/barbearia` (detalhes da barbearia), `/cliente/barbeiro/:barberId/avaliacoes` (avaliações do barbeiro), e `/suporte` (chat de suporte com IA).

## ETAPA 5 — LANDING PAGE E DESCOBERTA DE BARBEARIAS

A rota `/` renderiza a página `Index.tsx`, que exibe uma landing page com identidade visual premium da marca DUB. A tela apresenta um sistema orbital animado com ícones de ferramentas de barbearia (tesoura, máquina, poste de barbeiro) e avatares de pessoas girando em espirais ao redor de uma estrela central, criando uma sensação visual de "galáxia". Três espirais de Arquimedes são geradas via SVG com a função `buildSpiralPath`, que calcula pontos de uma espiral parametrizada por raio inicial, raio final e número de voltas. Os ícones são posicionados ao longo dessas espirais usando interpolação trigonométrica na função `posOnSpiral`. O botão principal "Encontrar Barbearias" navega para `/escolher-barbearia`, que é a página de descoberta multi-tenant. Esta página (`EscolherBarbearia.tsx`) carrega todos os tenants ativos do banco de dados junto com suas unidades (tabela `tenant_unidades`), e calcula a distância do usuário até cada unidade usando a fórmula de Haversine para distâncias geodésicas e uma estimativa de tempo de deslocamento baseada em velocidade média urbana de 25 km/h com fator de correção de 1.2x. As barbearias são exibidas em cards com informações de localização e distância, e ao selecionar uma, o sistema salva o `tenant_id` escolhido no campo `barbearia_preferida_id` da tabela `profiles` do usuário e o redireciona para o login ou dashboard.

## ETAPA 6 — AUTENTICAÇÃO E CADASTRO

A página `Auth.tsx` implementa tanto o fluxo de login quanto de cadastro em uma única tela, alternando entre os modos via query parameter `?mode=login` ou `?mode=signup`. O cadastro utiliza validação com Zod, definindo schemas rigorosos para nome (2-100 caracteres), email válido, telefone (validado pela função customizada `validatePhone` em `src/lib/validators.ts`), CPF (validado algoritmicamente pela função `validateCPF` que verifica os dígitos verificadores), e senha (mínimo 6 caracteres). Antes de criar a conta, o sistema invoca a Edge Function `check-duplicate-signup` para verificar se o CPF, telefone ou email já existem no banco, evitando duplicidades. O cadastro é feito via `supabase.auth.signUp()`, que cria o usuário na tabela `auth.users` do Supabase e envia um email de confirmação. Os metadados do usuário (nome, telefone, CPF, `signup_origin`) são passados via `options.data`, e um trigger no banco de dados (não visível no frontend) popula a tabela `profiles` com esses dados. O `signup_origin` pode ser `dub_exclusive` (cadastro direto pela DUB) ou `discover` (veio pelo fluxo de descoberta). Após o login bem-sucedido, a função `checkUserRoleAndRedirect` consulta a tabela `user_roles` para verificar se o usuário tem role `admin` — caso positivo, ele é imediatamente deslogado com uma mensagem de que o app é exclusivo para clientes, impedindo que administradores acessem o app de cliente. Se o usuário veio com um `tenant` pré-selecionado via query parameter (fluxo de link público), o `barbearia_preferida_id` é salvo no perfil antes do redirecionamento.

## ETAPA 7 — DASHBOARD DO CLIENTE (RENDERIZAÇÃO PROGRESSIVA)

A página `/cliente` (`Cliente.tsx`) é o coração do aplicativo, com aproximadamente 1200 linhas de código, e implementa um sistema de renderização progressiva em quatro camadas independentes. Ao montar, o componente verifica a sessão via `supabase.auth.getSession()` — se não houver sessão, redireciona para `/auth`. Caso haja sessão, inicia o carregamento orquestrado em duas fases: primeiro carrega a **Camada 1 (Perfil e Tenant)** chamando `loadProfileData`, que busca o perfil completo do usuário na tabela `profiles` e, se houver `barbearia_preferida_id`, busca o nome da barbearia na tabela `tenants`. Somente após o perfil estar carregado (porque dele depende o `tenant_id`), as três camadas seguintes são disparadas em paralelo via `Promise.all`: a **Camada 2 (Agendamentos)** via `loadAppointmentsData`, a **Camada 3 (Fidelidade e Assinaturas)** via `loadLoyaltyData`, e a **Camada 4 (Barbeiros da Barbearia)** via `loadShopData`. Cada camada tem seu próprio estado de loading (`profileLoading`, `appointmentsLoading`, `loyaltyLoading`, `shopLoading`), seu próprio guard de condição de corrida via `useRef` (`profileLoadRef`, `appointmentsLoadRef`, etc.), e persiste seus resultados no `sessionStorage` com TTL configurável usando as funções `setCache` e `getCache` do arquivo `src/utils/cache.ts` — o perfil é cacheado por 60 minutos, os agendamentos por 5 minutos, a fidelidade por 5 minutos e os dados da barbearia por 30 minutos. Na inicialização, o componente tenta restaurar dados do cache para exibição imediata (evitando tela branca), e depois atualiza com dados frescos do servidor.

A **Camada 2 (Agendamentos)** faz quatro queries paralelas via `Promise.all`: busca os agendamentos visíveis com status pendente ou confirmado (limitado a 3), junto com joins para nome do serviço, apelido do barbeiro e dados de pagamento; busca todos os pagamentos do usuário; busca as reservas pendentes (tabela `pending_bookings`); e busca cancelamentos recentes feitos em massa (últimos 2 dias). A **Camada 3 (Fidelidade)** consulta cinco fontes em paralelo: créditos disponíveis via RPC `get_user_available_credits`, pontos na tabela `pontos`, contagem de agendamentos concluídos, resgates ativos (cortes grátis), e disponibilidade de resgates. Após isso, faz uma busca sequencial pela assinatura ativa do usuário na tabela `assinaturas` (com join na tabela `planos` para obter nome e limite de agendamentos), e se houver assinatura ativa, calcula o uso no ciclo atual via RPC `count_subscription_uses_in_cycle`. Se não houver assinatura ativa, busca assinaturas pendentes (status `suspended` ou `pending_cash`) e, na ausência dessas, busca assinaturas canceladas nos últimos 30 dias para exibir um banner de plano expirado. A **Camada 4 (Barbeiros)** consulta os barbeiros ativos e não-deletados do tenant selecionado, incluindo suas avaliações (tabela `barbeiro_avaliacoes`), e calcula a média de rating e total de reviews para cada barbeiro.

## ETAPA 8 — REALTIME E SINCRONIZAÇÃO AO VIVO

O dashboard mantém três canais Realtime do Supabase ativos simultaneamente para receber atualizações instantâneas sem necessidade de polling. O **Canal 1 (canal-agendamentos)** escuta mudanças na tabela `agendamentos` filtradas por `user_id` e na tabela `pending_bookings`. Quando um novo agendamento é inserido, um toast de sucesso é exibido e os dados são recarregados. Quando um agendamento é atualizado, o sistema verifica o novo status: se passou para `confirmed`, exibe "✅ Agendamento confirmado pelo barbeiro!"; se passou para `completed`, exibe "🎉 Atendimento concluído!"; se foi cancelado pelo admin, exibe "❌ Agendamento cancelado pela barbearia". Se o agendamento tiver `visivel_para_usuario === false`, ele é removido da lista local sem recarregar do servidor. O **Canal 2 (canal-fidelidade)** escuta mudanças nas tabelas `assinaturas`, `pontos`, `resgates`, `promocoes` e `planos`, todas filtradas por `user_id` ou `tenant_id`, recarregando a camada de fidelidade quando qualquer alteração é detectada. O **Canal 3 (canal-barbeiros)** escuta mudanças na tabela `barbeiros` filtradas por `tenant_id`, recarregando a lista de barbeiros da barbearia. Todos os canais implementam detecção de erro e reconexão automática: se um canal entra em estado `CHANNEL_ERROR` ou `TIMED_OUT` (e o canal existe há mais de 5 segundos, para ignorar erros transitórios), o sistema agenda uma reconexão completa após 30 segundos, reinicializando todos os canais e recarregando todas as camadas de dados.

## ETAPA 9 — TRATAMENTO DE ERROS DE DADOS

O hook customizado `useDataError` centraliza o tratamento de erros de carregamento. Cada camada reporta seus erros via `reportError(camada, erro)`, e o hook acumula esses erros em um array. Quando há erros, um toast não-bloqueante é exibido com a mensagem "Alguns dados podem estar desatualizados" e um botão "Tentar novamente" que dispara `retryAllLayers`, uma função que reseta os guards de condição de corrida, limpa os erros e reexecuta todas as quatro camadas em paralelo usando `Promise.allSettled` (para que a falha de uma camada não impeça as outras de completar). O sistema implementa um limite de 2 tentativas automáticas de retry — após isso, suprime o toast para não poluir a interface, seguindo o princípio de degradação graceful.

## ETAPA 10 — FLUXO DE AGENDAMENTO

A página `ClienteAgendar.tsx` (com aproximadamente 2700 linhas) implementa o fluxo completo de reserva em 6 passos sequenciais. Na inicialização, o componente busca a sessão do usuário, carrega o perfil para obter o `tenant_id` da barbearia preferida e a unidade preferida (`unidade_preferida_id`), carrega as unidades do tenant (se houver múltiplas), e então determina se o usuário veio de um fluxo de assinatura (via query parameter `plan=true`). No **Passo 1 (Seleção de Profissional)**, os barbeiros são carregados da tabela `barbeiros` filtrados por `tenant_id` e opcionalmente por `unidade_id`, exibidos em cards com foto, apelido e avaliação média (calculada via o hook `useBarberRatings`). No **Passo 2 (Seleção de Serviço)**, os serviços são carregados da tabela `servicos` filtrados por tenant, e o sistema suporta seleção múltipla com quantidade por serviço. Ao selecionar um barbeiro, o sistema carrega as durações personalizadas desse barbeiro via tabela `barbeiro_servico_duracao`, que permitem que cada profissional defina tempos diferentes para o mesmo serviço. No **Passo 3 (Seleção de Data)**, um calendário premium (`PremiumCalendar`) exibe os próximos 45 dias, com dias fechados (baseados na configuração de horários do barbeiro via hook `useBarberBusinessHours`) marcados como indisponíveis. No **Passo 4 (Seleção de Horário)**, o hook `useSlotAvailability` calcula os slots disponíveis chamando a Edge Function `check-availability`, que verifica conflitos com agendamentos existentes, horários excepcionais, pausas de almoço e delay entre serviços. No **Passo 5 (Pagamento)**, o usuário escolhe entre dinheiro, cartão (via Asaas), PIX (via Asaas), carteira digital (saldo de créditos), ou plano (se for assinante ativo). No **Passo 6 (Confirmação)**, o agendamento é criado atomicamente via Edge Function `atomic-booking`, que implementa validações server-side de disponibilidade, integridade financeira e reserva temporal para evitar double-booking.

Se o usuário é um assinante ativo, o sistema detecta isso via query parameter `plan=true` e ativa o **fluxo ultra-rápido de plano**: o serviço e barbeiro vinculados à assinatura são pré-selecionados automaticamente, e o usuário é redirecionado diretamente para o Passo 3 (Data), pulando a seleção de profissional e serviço. O método de pagamento é automaticamente definido como `plano`, e o preço é zero.

## ETAPA 11 — INTEGRAÇÃO DE PAGAMENTOS (ASAAS)

O sistema de pagamentos integra com o gateway Asaas através de múltiplas Edge Functions. Para pagamentos PIX, a Edge Function `create-asaas-pix` gera um QR Code e payload PIX dinâmico. O roteamento de chaves API é dinâmico: o sistema primeiro verifica se o barbeiro do agendamento possui uma chave API própria na tabela `barbeiros_private`, e caso contrário, utiliza a conta principal como fallback. Webhooks do Asaas são recebidos pela Edge Function `asaas-webhook`, que processa eventos como `RECEIVED`, `CONFIRMED` e `RECEIVED_IN_CASH`, implementando idempotência por verificação do `gateway_payment_id` antes de converter reservas em agendamentos efetivos. Para pagamentos via cartão, a Edge Function `create-asaas-card` processa a cobrança diretamente. As assinaturas recorrentes são gerenciadas pelas Edge Functions `create-subscription-pix` e `create-subscription-card`, com verificação de status via `check-subscription-pix`. O cancelamento de assinaturas é feito pela Edge Function `cancel-subscription`, que encerra o contrato no gateway e marca localmente como `cancelled`.

## ETAPA 12 — CARTEIRA DIGITAL E CRÉDITOS

O sistema de carteira digital opera em duas camadas: créditos (gerados por reembolsos de cancelamentos ou promoções) e saldo de carteira (depósitos em dinheiro). Os créditos são armazenados na tabela `creditos`, onde cada registro representa um valor unitário com campos `usado`, `expires_at` e `agendamento_usado_id`. A função de banco de dados `use_credits_atomic` implementa o consumo atômico de créditos usando `FOR UPDATE` locks para evitar race conditions, processando créditos mais antigos primeiro (FIFO) e suportando uso parcial (dividindo um crédito em duas entradas). O saldo da carteira é gerenciado pela tabela `wallet_balances` e pela Edge Function `wallet-operations`, que processa depósitos e saques com validação de PIN (armazenado via `wallet-pin`). A função `get_or_create_wallet_balance` garante que todo usuário tenha um registro de saldo, criando-o com valor zero na primeira consulta. Saques são validados pela função `validar_saque`, que verifica saldo disponível, valor mínimo (R$ 1,00), e limite de 3 saques por dia.

## ETAPA 13 — SISTEMA DE FIDELIDADE E RESGATES

O programa de fidelidade funciona com um sistema de pontos acumulativos. Cada agendamento concluído libera um ponto (campo `ponto_liberado` na tabela `agendamentos`), e os pontos são somados na tabela `pontos`. Quando o usuário atinge o número necessário de pontos (configurado por tenant na tabela `promocoes`, campo `pontos_necessarios`, com padrão de 8), um resgate é gerado na tabela `resgates` com status `available`. Ao agendar usando um resgate, o trigger de banco de dados `consume_redemption_on_appointment_insert` é ativado: ele seleciona o resgate mais antigo disponível com `FOR UPDATE SKIP LOCKED` (prevenindo corrida entre sessões concorrentes), marca-o como `used`, e vincula ao agendamento. Se o agendamento for cancelado, o trigger `release_redemption_on_appointment_cancel` devolve o resgate ao status `available` (desde que não tenha expirado). O modal `PointsDetailModal` exibe ao usuário seu progresso visual, mostrando quantos pontos faltam para o próximo corte grátis.

## ETAPA 14 — SISTEMA DE ASSINATURAS (PLANOS)

As assinaturas são gerenciadas na tabela `assinaturas`, vinculando o usuário a um plano (tabela `planos`) com campos como `limite_agendamentos_mes`, `preco_mensal` e `servico_id` (serviço específico coberto pelo plano). O status da assinatura pode ser `active`, `suspended`, `pending_cash`, `cancelled`, entre outros. A função `auto_suspend_expired_cash_subscriptions` roda periodicamente para suspender assinaturas com pagamento em dinheiro cujo `next_billing_date` já passou. Para assinantes, o componente `PlanTrackerCard` exibe visualmente o uso do plano no ciclo atual (ex: "2/4 cortes usados"), e o `PlanExpiredBanner` incentiva a renovação quando o plano vence. A contagem de usos no ciclo é feita pela RPC `count_subscription_uses_in_cycle`, que conta registros na tabela `plano_agendamentos_usos` dentro do intervalo de datas do ciclo.

## ETAPA 15 — SISTEMA DE AVALIAÇÕES

Após cada atendimento concluído, o sistema verifica se há avaliações pendentes através do hook `usePendingReviews`, que busca agendamentos com status `completed` que ainda não possuem registro na tabela `barbeiro_avaliacoes`. O modal de avaliação (`BarberReviewModal`) é aberto automaticamente uma única vez por sessão, mostrando o nome e foto do barbeiro. Avaliações dispensadas são persistidas no `localStorage` com a chave `dismissed_review_ids`, garantindo que o modal nunca reapareça para aquele agendamento específico. A avaliação inclui um rating de 1 a 5 estrelas e comentário opcional, validados server-side pelo trigger `validate_barber_review_rating`. Há uma janela de edição de 24 horas controlada pelo trigger `enforce_barber_review_edit_window`. O componente `PendingReviewBanner` exibe um banner discreto no dashboard quando há avaliações pendentes.

## ETAPA 16 — WEBHOOKS E INTEGRAÇÕES EXTERNAS

O arquivo `src/lib/webhookService.ts` (com aproximadamente 940 linhas) implementa um sistema completo de eventos para integração com serviços externos (WhatsApp via n8n, CRM, etc.). Cada ação significativa do sistema dispara um evento via a Edge Function `send-webhook-event`, que consulta a tabela `webhook_config` para obter a URL do webhook e verificar se está ativo. Os eventos incluem: `agendamento_criado`, `agendamento_confirmado`, `agendamento_cancelado`, `remarcacao_solicitada`, `remarcacao_concluida`, `atendimento_iniciado`, `atendimento_finalizado`, entre outros. Cada evento enriquece automaticamente os dados com informações completas do cliente (nome, telefone, CPF, email, telefone formatado para WhatsApp no padrão `NUMERO@s.whatsapp.net`) e do barbeiro, obtidos via funções auxiliares `getClienteCompleto` e `getBarbeiroCompleto`. A integração com WhatsApp é feita via trigger de banco de dados `trg_send_confirm_message_on_barber_confirm`, que, ao detectar que o barbeiro confirmou um agendamento, busca a instância WhatsApp conectada (tabela `whatsapp_instances`), monta a mensagem de confirmação (usando templates da tabela `mensagem_templates` ou um template padrão), e envia via webhook para a API de disparo. O sistema implementa detecção de walk-in (quando o `user_id` do agendamento é o mesmo do barbeiro) para evitar enviar mensagem para o próprio barbeiro, e detecção de cliente sem telefone para pular o envio graciosamente.

## ETAPA 17 — SUPORTE VIA IA

A rota `/suporte` renderiza o `SupportChat`, que implementa um chat de suporte assistido por inteligência artificial. O componente `SupportChatInterface` gerencia o histórico de conversas armazenado na tabela `support_conversations` e mensagens na tabela `support_messages`. As respostas são geradas pela Edge Function `ai-support-chat`, que utiliza a API da OpenAI para gerar respostas contextualizadas sobre os serviços e funcionalidades do aplicativo. O componente `SupportChatBubble` renderiza um botão flutuante de acesso rápido ao suporte em todas as páginas autenticadas. O sistema também inclui feedback do usuário sobre as respostas (tabela `ai_feedback`) e log de ações executadas pela IA (tabela `ai_actions_log`).

## ETAPA 18 — NOTIFICAÇÕES E LEMBRETES

O hook `useNotificationManager` gerencia notificações push e sonoras para o usuário. As notificações são armazenadas na tabela `notificacoes` e exibidas através do `NotificationsSheet`. Lembretes de agendamento são gerenciados pela Edge Function `appointment-reminders`, que agenda e envia lembretes via WhatsApp antes do horário do agendamento, com logs detalhados na tabela `agendamento_lembretes_log`. O sistema suporta diferentes tipos de lembretes: confirmação de agendamento, lembrete de véspera, e lembrete no dia.

## ETAPA 19 — SEGURANÇA E CONTROLE DE ACESSO

O sistema implementa múltiplas camadas de segurança. A tabela `user_roles` armazena roles separadamente do perfil (nunca no campo do usuário), podendo ser `admin`, `moderator`, `cliente` ou `tenant_admin`. A função `is_admin()` verifica roles via query na tabela, e `has_role()` é uma função `SECURITY DEFINER` que bypassa RLS para verificação segura. Row-Level Security (RLS) é habilitado em todas as tabelas sensíveis, com policies que utilizam `auth.uid()` para filtrar dados do usuário autenticado. O sistema de dispositivos autorizados (`dispositivos_autorizados` e `dispositivos_conectados`) tracked dispositivos que acessam o app, com fingerprinting via `useDeviceFingerprint` e verificação via a função `is_device_authorized`. Tentativas de acesso ao módulo financeiro são logadas na tabela `financeiro_auth_attempts`. A Edge Function `admin-reset-password` permite reset de senha com verificação de role admin. Para o módulo financeiro, existe um sistema de senha separada (tabela `financeiro_security_config`) com sessões temporárias (tabela `financeiro_auth_sessions`), garantindo uma segunda camada de autenticação para operações sensíveis.

## ETAPA 20 — CACHE E PERFORMANCE

O sistema utiliza uma estratégia de cache granular no `sessionStorage` com TTLs diferenciados por tipo de dado. O utilitário `src/utils/cache.ts` implementa `setCache(key, data, ttlMinutes)` que armazena dados com timestamp de expiração, e `getCache<T>(key)` que retorna `null` para dados expirados, removendo-os automaticamente. O cache do perfil dura 60 minutos pois muda raramente, enquanto agendamentos e fidelidade usam 5 minutos por serem mais dinâmicos, e dados da barbearia (barbeiros) usam 30 minutos. Na inicialização do dashboard, o componente tenta restaurar todos os caches disponíveis para exibição instantânea (eliminando a sensação de tela em branco), e depois substitui com dados frescos do servidor. Os guards de condição de corrida via `useRef` (`profileLoadRef`, etc.) impedem que múltiplas chamadas concorrentes ao mesmo loader se sobreponham, especialmente quando eventos Realtime disparam recargas enquanto uma carga anterior ainda está em andamento. Todo o roteamento de páginas usa `React.lazy()` com code-splitting, e o bundler Vite gera chunks separados por rota.

## ETAPA 21 — MULTI-TENANCY E ISOLAMENTO DE DADOS

O multi-tenancy é implementado via campo `tenant_id` presente nas tabelas `barbeiros`, `servicos`, `planos`, `promocoes`, `agendamentos` (indiretamente via barbeiro), entre outras. A função utilitária `buildBarberQuery` em `src/utils/tenantQuery.ts` centraliza a lógica de filtro por tenant, tratando o caso legado onde `tenant_id` é `null` (Barbearia DUB original, antes da migração multi-tenant). A função `applyTenantFilter` permite aplicar o filtro de tenant a qualquer query existente de forma genérica. No fluxo do cliente, profissionais, serviços, promoções e disponibilidade são sempre filtrados pelo `tenant_id` da barbearia selecionada (armazenado em `profiles.barbearia_preferida_id`). Se o cliente tenta acessar o agendamento sem barbearia vinculada, é redirecionado para `/cliente/barbearia` ou `/escolher-barbearia`. Cada tenant pode ter múltiplas unidades (tabela `tenant_unidades`), e o sistema de unidades permite que barbeiros sejam associados a unidades específicas ou disponíveis em todas (quando `unidade_id` é `null`). Os tenants são criados com onboarding completo, e ao completar o onboarding, o trigger `create_trial_on_onboarding_complete` cria automaticamente uma assinatura trial de 7 dias na tabela `tenant_assinaturas`, e o trigger `create_default_loyalty_promotion` cria uma promoção de fidelidade padrão desabilitada.

## ETAPA 22 — COMPONENTES DE UI E DESIGN SYSTEM

O design system segue uma estética "Dark Premium" com tokens semânticos definidos em `src/index.css`: `--background` (preto puro no dark, branco no light), `--foreground`, `--card`, `--primary` (vermelho), `--secondary` (dourado), `--muted`, `--accent`, `--border`, e `--destructive`, todos em formato HSL para compatibilidade com Tailwind CSS. Componentes nunca usam cores diretas — sempre referenciando tokens via classes como `bg-background`, `text-foreground`, `bg-primary`, etc. Os componentes de UI são baseados em shadcn/ui (Radix UI primitives) customizados com variantes específicas via `class-variance-authority`. Animações utilizam Framer Motion com padrões consistentes: `initial={{ opacity: 0, y: 6 }}` para entrada de cards em lista com stagger de 30ms, e `AnimatePresence` para transições entre views. A navegação inferior (`BottomNavigation`) segue o padrão iOS com 4 itens (Início, Agenda, Perfil, Suporte), posicionada fixamente na parte inferior com `pb-[env(safe-area-inset-bottom)]` para compatibilidade com notch/home indicator. Todos os cards de interação implementam feedback tátil com `active:scale-[0.99]`, e áreas scrolláveis usam `overscroll-contain` para evitar scroll inercial no container pai.
